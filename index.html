0.🧭 Agent Orchestrator

Pilote le parcours complet de bout en bout, de la User Story aux tests Jenkins, avec validation humaine à chaque étape clé.
Rôle:
Superviseur unique avec lequel l'utilisateur interagit via le panneau de l'extension VS Code. Coordonne séquentiellement les 6 agents spécialistes.

Mission:

Agent qui coordonne le pipeline complet, de la User Story jusqu'aux jobs Jenkins, en appelant les autres agents dans le bon ordre.

  • Ne génère rien moi-même : j'orchestre AutomationArchitect, GherkinSmith, TestCaseToJira, tnra_ia et AutomationHealer.
  • fais valider chaque étape par l'utilisateur avant de passer à la suivante.
  • Garantis qu'aucun ticket Jira ni aucune exécution n'est lancé sans accord explicite.

Cas d'usage:

  • Automatiser de bout en bout une User Story : scénarios, tickets de test, suite Robot, jobs Jenkins, exécution.
  • Garder la main sur un enchaînement long avec des points de contrôle clairs.
  • Choisir, parmi les scénarios générés, ceux à créer dans Jira.
  • Enchaîner automatiquement sur le diagnostic si un build Jenkins échoue.

Inputs/Outputs:

Inputs

Outputs
  • User Story (clé ou URL Jira, ou description libre)
  • Dossier de sortie (optionnel)
  • URL du dossier Jenkins (optionnel)
  • Validations successives de l'utilisateur)
  • Fichier .feature (scénarios Gherkin validés)
  • Tickets de test Jira (via JiraTestCreator)
  • Fichier de suite Robot Framework (.robot)
  • Jobs Jenkins créés après simulation

1.🏛️ Automation Architect

Audite le projet Robot Framework, s'assure du respect des normes ISTQB et propose une structure type.

Rôle:
Analyse le workspace pour vérifier s'il s'agit d'un projet Robot Framework conforme, et propose le cas échéant d'initialiser une arborescence type

Mission:

Agent qui audite l'architecture d'un projet Robot Framework et formalise ses bonnes pratiques dans un guide (InstructionsTemplate.md).

  • Je détecte si un projet Robot Framework existe déjà dans le workspace.
  • S'il existe, je l'audite : conventions Gherkin, structure des steps, Page Object Model, règles de locators, anti-patterns.
  • Sinon, je propose de créer un projet conforme aux normes ISTQB et aux standards TNRA APPUI.
  • Je travaille en arrière-plan, sans console dédiée, et je ne crée ni ne modifie rien sans validation explicite.

Cas d'usage:

  • Démarrer un nouveau projet d'automatisation avec une arborescence normalisée.
  • Formaliser les bonnes pratiques d'un projet déjà en place (onboarding d'un automaticien).
  • Auditer un projet existant et repérer ses anti-patterns.
  • Servir de point de contrôle avant toute génération : l'Orchestrator m'appelle en étape 0, avant GherkinSmith.

Inputs/Outputs:

Inputs

Outputs

  • Nom du projet
  • Confirmation de l'utilisateur)
  • InstructionsTemplate.md
  • Arborescence de projet (si création validée)

2.✍️ GherkinGenerator

Traduit toute expression de besoin fonctionnel en scénarios Gherkin normés en français (Soit / Quand / Alors).

Rôle:

Prend une User Story (Jira, Confluence, doc Word/Excel/PDF, texte libre) et la transforme en scénarios Gherkin complets (nominal, alternatif, erreur).

Mission:

Agent qui transforme un besoin métier en scénarios de test Gherkin en français, puis en fichier Robot Framework prêt à automatiser.

  • Je lis la source (ticket, page, document, texte) et je restitue le besoin compris.
  • J'inventorie toutes les règles de gestion (RG-01, RG-02…) avant d'écrire un seul scénario.
  • Je rédige des scénarios Gherkin (Soit / Quand / Et / Alors) avec les techniques ISTQB adaptées.
  • Je prouve la couverture avec une matrice de traçabilité règle → scénario.
  • Je ne génère le .robot qu'après validation du Gherkin par l'utilisateur.
Cas d'usage:
  • Une User Story vient d'être créée dans Jira et il faut en tirer les cas de test.
  • Un compte-rendu de réunion, un email ou un cahier des charges doit être transformé en tests.
  • Une suite Robot existante doit être enrichie de nouveaux cas, en réutilisant ses keywords.
  • Une spécification Confluence ou un fichier Excel, Word ou PDF doit être converti en scénarios.

Inputs/Outputs:

Inputs

Outputs
  • Clé ou URL Jira
  • URL Confluence
  • Suite Robot existante ,chemin .robot, .xlsx, .docx ou .pdf
  • Texte libre collé dans le formulaire
  • Résumé du besoin compris (à valider).
  • Scénarios Gherkin en français, comprenant :
    • 1 scénario nominal enrichi, avec annotations # Couvre : RG-xx ;
    • des cas d'erreur dérivés de chaque règle, regroupés en Plan du Scénario + Exemples ;
    • des scénarios alternatifs uniquement si de nouvelles règles le justifient.
  • Fichier .robot rangé dans la structure NRAF, produit après validation du Gherkin.

3.🎫 TestCaseToJira

Crée dans Jira Xray les cas de test Cucumber/Gherkin validés et gère la traçabilité IA (IAFlag).

Rôle:

Prend les scénarios validés par l'utilisateur et crée les tickets Jira de type Test avec marquage de traçabilité IA et liens avec la US.

Mission:

Agent qui transforme des scénarios Gherkin validés en cas de test Jira/Xray structurés.

  • Je crée un ticket de type « Test Xray » par scénario, avec le Gherkin conservé tel quel, sans conversion en steps classiques.
  • Je renseigne les champs Xray obligatoires et le marquage IA (IAFlag).
  • Je rattache le test à sa User Story et à sa suite ou plan de test quand ils sont fournis.
  • Si le ticket existe déjà, je le mets à jour au lieu d'en créer un nouveau.

Cas d'usage:

  • Tracer officiellement dans Jira les scénarios produits par GherkinGenerator, une fois validés.
  • Créer plusieurs tickets de test à partir d'une même Feature (un ticket par scénario).
  • Rattacher les tests à une User Story (traçabilité exigence → test) et à un Test Set ou dossier Cucumber.
  • Mettre à jour un ticket de test existant après évolution du scénario.

Inputs/Outputs:

Inputs

Outputs
  • Clé ou URL Jira
  • Nom du scénario Gherkin
  • User Story liée
  • Suite ou plan de test
  • Un ticket Jira par scénario
  • Marquage « Created » ou « Updated » (indicateur d'usage de l'IA)

Outils Ensemble des outils Copilot activés

  • Gain de temps : plus de saisie manuelle des tickets, un ticket par scénario en quelques secondes.
  • Fidélité : le Gherkin est conservé à l'identique, il peut être recopié dans un .feature.
  • Traçabilité : lien automatique entre le test, la User Story et la suite de test.
  • Uniformité : mêmes champs Xray et même titre [Feature] - Scénario d'un projet à l'autre.

4.📚 tnra_ia

Expert des socles Robot Framework La Poste, créateur de jobs Jenkins Docker SOD et exécuteur de builds.

Rôle:

Consulte le RAG GitLab en direct sans stockage local, convertit le Gherkin en suites TNRA et déploie les jobs Jenkins conteneurisés.

Mission:

Agent expert des socles APPUI pour la réalisation de TNRA (Tests de Non-Régression Automatisés) avec Robot Framework.

  • réponds aux questions sur les socles TNRA : Web, API, Kafka, Mobile, DDT, Xray, Jenkins, etc.
  • m'appuie exclusivement sur la documentation RAG officielle lue dans GitLab, sans installation locale.
  • Pour l'Orchestrator, je convertis un .feature validé en suite .robot conforme aux standards TNRA.
  • exécute les skills Jenkins : création des jobs de test et déclenchement des builds.

Cas d'usage:

  • Poser une question sur un socle TNRA (« comment lire un topic Kafka en Robot Framework ? »).
  • Convertir un .feature en suite Robot selon le template TNRA BDD.
  • Créer un job Jenkins par ticket de test, dans un dossier Jenkins donné.
  • Lancer un build Jenkins et suivre son statut jusqu'à la fin.
  • Aider un automaticien à démarrer : arborescence du projet, keywords de base, remontées vers Xray.

5.▶️ TestExecutor

Exécuteur de tests multi-frameworks (Robot Framework, Pytest, Playwright) en local ou via Jenkins.

Rôle:

Route dynamiquement les demandes d'exécution, prend en charge les profils d'environnement et permet la relance ciblée (--rerun).

Mission:

Agent qui exécute les tests automatisés et explique pourquoi ils échouent.

  • lance un test, une suite ou un job Jenkins. Je prends en charge Robot Framework, pytest et Playwright, en local ou via Jenkins.
  • ne rejoue pas les tests à la main : je détecte la source, le framework et l'environnement, puis je lance la bonne commande.
  • Quand un test échoue, je produis un diagnostic de cause racine (méthode ISTQB). Je distingue un bug applicatif, un problème de script et un problème d'environnement.
  • propose une correction minimale et réversible, uniquement après accord explicite de l'utilisateur.

Cas d'usage:

  • Rejouer un test après correction.
  • Vérifier une non-régression.
  • Lancer une campagne à partir d'un ticket Jira.

Inputs/Outputs:

Inputs

Outputs

  • Nom de job ou URL Jenkins

  • Résultats techniques (commande exécutée, artefacts)
  • Diagnostic (cause racine, catégorie, step et keyword en cause)
  • Captures et preuves (screenshots, extraits de log)

6.🩺 AutomationHealer

Diagnostique les échecs Robot/Jenkins (ISTQB), résout les tests instables (Flaky), applique les patchs et relance le test.

Rôle:

Analyse les logs d'échec, isole la root cause (bug applicatif vs script vs environnement), stabilise les sélecteurs et relance le tir pour valider la guérison.

Mission:

Agent qui diagnostique un test automatisé en échec et le répare de façon contrôlée.

  • analyse les artefacts d'exécution Robot Framework et la chaîne complète : scénario Gherkin → step Robot → keyword → code Python.
  • classe la cause dans une seule catégorie : bug applicatif, problème de script ou problème d'environnement.
  • propose la plus petite correction réversible (self-healing d'un locator cassé, synchronisation, assertion).
  • détecte les tests instables (flaky) à partir de l'historique de plusieurs runs.
  • ne conclus jamais à un « bug applicatif » avant d'avoir écarté le script et l'environnement.

Cas d'usage:

  • Un test échoue en CI/CD ou en local et la cause n'est pas évidente.
  • Un locator est cassé après une évolution de l'interface.
  • Un test passe puis échoue sans changement de code (flakiness).
  • Auditer les locators d'un projet, ou refactorer des tests instables, dupliqués ou difficiles à maintenir.
  • Détecter une anomalie fonctionnelle à confirmer auprès du métier.

Inputs/Outputs:

Inputs

Outputs
  • Description de l'échec
  • Artefacts d'exécution
  • Corrélation technique (Scénario Gherkin, step Robot, keyword ou fonction Python concernés)
  • Diagnostic (Cause racine, catégorie (bug applicatif, script ou environnement), preuve principale)
  • Correctif
  • Résumé (Scénario ou test impacté, statut de l'analyse)

Guide Pas-à-Pas d'une Session Type (Mode Démo / Production

Chargement des Agents

Avant de pouvoir utiliser les agents IA, il est indispensable de les charger dans votre IDE. Cette étape est souvent oubliée et est la cause principale de l'absence des agents dans le panneau de chat.

⚠️ Étape critique — Sans rechargement, aucun agent ne sera visible

Les fichiers .agent.md contiennent la définition des agents. Pour que GitHub Copilot les prenne en compte dans le chat, il est impératif d'exécuter la commande de rechargement des agents.

Procédure de chargement via GitHub Copilot (commune aux deux profils)

:one: .Cloner ou mettre à jour le dépôt des agents

Assurez-vous d'avoir la dernière version du dépôt GitLab sur la branche dev_RIM.
Automatisé : git clone https://git.net-courrier.extra.laposte.fr/GROUPE_CAPITALISATION/ia4test_capgemini.git -b dev_RIM
Fonctionnel : Demander l'archive .zip du dossier agents/ à l'équipe DevOps.

:two: .Ouvrir le dossier workspace dans VS Code

Faites Fichier → Ouvrir le dossier… et sélectionnez la racine du projet cloné (le dossier contenant .vscode/ et agents/). Il est essentiel d'ouvrir le dossier racine et non un sous-dossier.

:three:. Recharger les agents via la palette de commandes (Ctrl+Shift+P)

Dans VS Code :
   1. Appuyez sur le raccourci clavier Ctrl+Shift+P (ou Cmd+Shift+P sous macOS).
   2. Tapez : Agent: Recharger les agents (ou Chat: Reload Agents).
   3. Appuyez sur Entrée pour valider.
       Note : Vous pouvez également cliquer sur le bouton de rechargement (icône ↻) situé dans le panneau de l'extension GitHub Copilot.
   4. GitHub Copilot rescannera le dossier agents/ et chargera l'ensemble des définitions .agent.md.
⌨️ Ctrl + Shift + P → tapez Agent: Recharger les agents (ou ↻ dans l'extension GitHub Copilot)

:four: .Vérifier la détection des agents

Dans la fenêtre de chat GitHub Copilot, tapez @ pour déclencher l'autocomplétion. Vous devez voir apparaître la liste des agents chargés (ex : @TestFactoryOrchestrator, @GherkinSmith…). Si un agent est absent, répétez l'étape 3.

:five: .Démarrer le(s) serveur(s) MCP

Une fois les agents chargés, démarrez MCP via la palette de commandes : Ctrl+Shift+P → « MCP: Start Server ».
Sélectionnez jira-mcp (profil Fonctionnel) ou jira-mcp + gitlab-mcp (profil Automatisé).
Vérifiez que le statut passe à 🟢 Running dans la barre d'état VS Code.

:six:. Configurer les outils disponibles (Configure Tools) ⚙️ Gate

Dans le panneau de chat GitHub Copilot, cliquez sur « Configure Tools » (icône ⚙️ en haut à droite du chat). Activez uniquement les outils correspondant à votre profil. Voir les maquettes ci-dessous.

Guide Pas-à-Pas d'une Session Type (Mode Démo / Production

Voici la procédure opérationnelle standard pour exécuter une campagne complète :

📌 Distinction selon votre profil utilisateur :

  • Testeurs Fonctionnels : Vous réalisez la préparation Jira, le rechargement de vos agents (Ctrl+Shift+P) et la génération Gherkin / Jira Xray (Étapes 1, 2 et 3). Vous vous arrêtez après la création des tickets dans Jira.
  • Testeurs Automatisés : Vous déroulez l'intégralité du pipeline ci-dessous (Étapes 1 à 6), incluant Jenkins et le self-healing Robot Framework.

Étape 1 : Préparation dans Jira

  1.  Identifier la User Story à automatiser (ex: <CLE_US>, type PROJ-101).
  2. Créer un ticket Test Execution dans Jira Xray (ex: <CLE_EXEC_ID>, type PROJ-200) intitulé : Campagne d'exécution - [NomFonctionnalité]. Noter sa clé (EXEC_ID).

Étape 2 : Lancement en Mode Debugging (F5) & Mode Console

  1.         Lancement du Débogage (Touche F5) : Dans la fenêtre VS Code où est ouvert le projet ia4test_capgemini, appuyer sur la touche F5 du clavier (ou menu Exécuter ➔ Démarrer le débogage).

        Une deuxième fenêtre VS Code s'ouvre automatiquement, intitulée [Extension Development Host]. C'est dans cette fenêtre que tournent les agents IA et l'extension.

           

  • Choix du dossier de test dans la nouvelle fenêtre :

                Dans cette fenêtre [Extension Development Host], faire Fichier ➔ Ouvrir le dossier... :

    • Option A — Projet existant (ex: Projet Collecte) : Ouvrir votre dossier de tests Robot Framework existant. Les agents s'initialisent et rechargent l'arborescence de vos tests en quelques secondes.
    • Option B — Nouveau projet / Dossier vide : Ouvrir un dossier vide. L'agent @AutomationArchitect se chargera d'initialiser pour vous l'arborescence standard (Suites/, Ressource/, Conf/).
  1. Ouverture du Mode Console :

                Pour ouvrir le panneau des formulaires interactifs, vous avez 3 accès rapides au choix :

                  Cliquer sur l'icône QA Agents dans la barre d'activité tout à gauche.

                  Cliquer sur le bouton  Agents QA tout en bas à gauche dans la barre d'état bleue de VS Code.

                  Appuyer sur Ctrl + Shift + P et taper « Agents QA: Ouvrir la console ».


             

  1. Sélection et saisie du formulaire @ TestFactoryOrchestrator.:
  • Sélectionner le formulaire TestFactoryOrchestrator.
  • Remplir les champs :
  • Source : Jira (ou Texte)
  • Clé Jira : <VOTRE_CLE_US> (ex: PROJ-101)
  • Titre de la fonctionnalité : <NomDeLaFonctionnalite> (ex: GestionPanier ou Authentification)
  • Projet Jira \ : <CODE_PROJET_JIRA> (ex: PROJ)*
  • URL Jenkins : https://<serveur-jenkins>/job/<VOTRE_APPLICATION>/job/TNR/job/<VOTRE_DOSSIER_JOB>/ (ex: URL de votre dossier PFE ou TNR sur PIC2)
  • Cocher les cases de validation.
  • Cliquer sur Préremplir le chat.
  1. Vérification des outils autorisés (Configure Tools) :

Avant d'envoyer votre message, assurez-vous en 2 secondes que les outils nécessaires (execute, agent, read, jira-laposte, gitLab-laposte) sont bien cochés dans le chat via l'icône 🛠️ (ou via Ctrl + Shift + P ➔ Chat: Configure Tools).

Étape 3 : Déroulement dans Copilot Chat

  1. Envoyer le message pré-rempli à @ TestFactoryOrchestrator..
  2. Audit : L'agent @AutomationArchitect confirme la structure du projet.
  3. Génération Gherkin : @GherkinSmith lit la US Jira et écrit Generated/<NomFonctionnalite>.feature.
  4. Validation utilisateur : Relire le fichier dans l'éditeur et taper Valider dans le chat.
  5. Sélection des tests : Indiquer à l'Orchestrateur quels scénarios créer (ex: "Créer les cas 1, 2 et 3").
  6. @TestCaseToJira crée les tickets de test correspondants dans Jira.


⛔ FIN DE SESSION POUR LE TESTEUR FONCTIONNEL :
Vos cas de test sont rédigés, validés et créés dans Jira Xray avec leurs liens de traçabilité. Les étapes suivantes (rattachement d'exécution, jobs Jenkins, Robot Framework et self-healing) sont prises en charge par les testeurs automatisés.

Étape 4 : Rattachement Xray (10 secondes)

Dans Jira, sur le ticket Test Execution (<CLE_EXEC_ID>) :

  • Cliquer sur Ajouter ➔ Tests existants.
  • Ajouter les clés des tests venant d'être créés.

Étape 5 : Création des Jobs Jenkins

L'Orchestrateur appelle @tnra_ia avec les paramètres préparés :

  • COFFRE_GIT = <nom_de_votre_coffre_git> (ex: nom de votre dépôt GitLab)
  • TNR_DEPLOY_TAG = <votre_branche_git> (ex: main ou votre branche de travail)
  • EXEC_ID = <CLE_EXEC_ID> (clé du ticket Test Execution Xray)

Les jobs sont créés dans le dossier Jenkins cible.

Étape 6 : Exécution et Self-Healing

  1. L'Orchestrateur demande si vous souhaitez exécuter les tests ➔ Répondre Oui.
  2. Les jobs tournent dans les conteneurs Docker SOD de La Poste.
  3. En cas d'échec : @AutomationHealer analyse immédiatement la console Jenkins, identifie la cause, propose la correction, l'applique après votre accord, et propose de relancer le job pour confirmer le passage au vert !

L'Orchestration de Bout en Bout (Pipeline Global)

Le pipeline orchestré relie l'ensemble des agents à travers 6 étapes séquentielles rythmées par des points d'arrêts de décision humaine (Quality Gates) :


:zero: 

Étape 0 — Audit Projet

@Orchestrator sollicite @AutomationArchitect pour vérifier que l'arborescence du workspace est conforme aux standards ISTQB.
:one: 

Étape 1 — Génération Gherkin

@GherkinSmith ingère la User Story et génère Generated/[Fonctionnalite].feature. Quality Gate 1 : relecture du testeur.

:two: 

Étapes 2 & 3 — Traçabilité Jira

Quality Gate 2 : choix des cas. @TestCaseToJira crée les tickets de test Xray correspondants avec IAFlag=Created.


:four:  

Étape 4 — Industrialisation TNRA

@tnra_ia prépare le socle Robot Framework BDD.rf/BDD.txt et configure les jobs conteneurisés Docker SOD sur Jenkins PIC2.

:five: 

Étape 5 — Exécution Jenkins

Validation du tir par le QA ➔ Lancement du build conteneurisé. Récupération du statut : SUCCESS ou FAILURE.


:six: 

Étape 6 — Self-Healing & Relance

Si échec ➔ @AutomationHealer analyse la root cause, propose un patch, l'applique après accord et relance le build pour valider le vert !
